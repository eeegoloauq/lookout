# lookout — спецификация v1

Редакция 2026-08-19, учтён ресёрч `docs/research.md`.

Лёгкий монитор доступности для homelab: HTTP/TLS/DNS-проверки, история, алерты в Telegram.
Заменяет Gatus. Один статический бинарь, ноль рантайм-зависимостей, декларативный YAML-конфиг.

Рабочий язык кода, комментариев, README и коммитов — **английский** (репо уедет в публичный OSS).
Этот документ — внутренний, на русском.

## 1. Принципы

1. **Молчание = всё хорошо, но молчание никогда не должно быть багом.** Главный урок эксплуатации
   Gatus: алерт, который «настроен по умолчанию», не сработал, и падение шло 6.5 часа незамеченным.
   Отсюда правило: **алертинг включён по умолчанию для каждой проверки**; чтобы проверка НЕ алертила,
   это надо написать явно (`alert: false`). Инверсия дефолта по сравнению с Gatus — сознательная.
2. **Простота дороже фич.** Ядро обязано быть читаемым за один присест. Всё, что не входит в v1, —
   не пишем «на будущее» и не оставляем заглушек.
3. **Ноль внешних зависимостей в том, что мы отдаём.** Страница статуса не тянет ни CDN, ни
   шрифты, ни иконки со стороны; телеметрии нет. Сами проверки по определению ходят наружу —
   список внешних точек закрытый и явный: DNS-резолвер из конфига, RDAP-реестр домена
   (адрес берётся из бутстрапа IANA), whois-сервер TLD, Telegram Bot API. Больше никого.
4. **Стоимость проверки осознанная.** Каждый тип проверки имеет свою частоту (см. §5). Всё, что можно
   получить даром из уже открытого соединения, берём даром.
5. **Конфиг деклоративный и валидируемый.** `lookout validate config.yaml` обязан ловить ошибки до
   запуска; падение процесса из-за кривого конфига = мониторинг стоит = недопустимо.

## 2. Не-цели v1

Графики и красивый дашборд (хватит JSON + текстовой страницы); многошаговые сценарии; проверки с
авторизацией сложнее статического заголовка; кластеризация; плагины; агенты на других хостах
(внешние точки обзора — не в v1, см. §5).

## 3. Технологии

- Go 1.26, только stdlib + минимум зависимостей. Разрешены ровно две:
  - `github.com/goccy/go-yaml` — парсер конфига. **Не `gopkg.in/yaml.v3`**: тот репозиторий
    архивирован (последний коммит апрель 2025, в README «THIS PROJECT IS UNMAINTAINED»).
    Проверено 2026-08-19.
  - `golang.org/x/net/proxy` — SOCKS5-клиент для алертера (в stdlib SOCKS5 нет). Сопровождается
    командой Go. Допустимая альтернатива, если хочется совсем без зависимостей: свой клиент
    SOCKS5 CONNECT без аутентификации — это ~60 строк, протокол тривиален.

  Любая третья — обосновать в PR отдельно. **Базы данных нет** (см. §9), cgo нет, бинарь статический.
- Сборка: `CGO_ENABLED=0 go build`, один бинарь + systemd-юнит. Docker не используем.
- Конфиг: YAML. Секреты: **только** через `${ENV_VAR}` из EnvironmentFile (0600), никогда в файле конфига.

## 4. Модель проверки

```yaml
checks:
  - name: Immich
    group: Services
    type: http                 # http | dns | domain
    url: http://lan-host:8080
    interval: 60s              # опционально, дефолт из defaults
    timeout: 5s
    headers: {Authorization: "Basic ${CAPTURE_BASIC_AUTH}"}
    expect:                    # все условия должны выполниться
      status: 200              # число, диапазон "200-299" или "<500"
      body: {".result.source.online": true}   # JSONPath-lite → ожидаемое значение
      body_contains: "ok"
      response_time: "<5s"
    alert: true                # дефолт true
```

Типы:
- `http` — GET (метод настраивается), проверка статуса/тела/времени. Для `https://` **побочно и
  бесплатно** извлекает срок сертификата из уже выполненного рукопожатия (§5.3).
- `dns` — запрос к резолверу (дефолт `8.8.8.8`, см. §9.2), `query_type` A/AAAA/MX/NS/TXT, ретраи
  обязательны (UDP теряется).
- `domain` — срок регистрации домена (§5.4).

**Язык условий.** НЕ повторяем строковый мини-язык Gatus (`"[STATUS] == 200"`) — он парсится в
рантайме и падает на опечатке. Условия — типизированная структура YAML, ошибки ловятся при валидации.

**Отсутствие поля ≠ несовпадение значения.** Путь в теле, которого нет, обязан давать отдельный
исход `malformed` с текстом «поле `.result.online` отсутствует в ответе», а не тихое «условие не
выполнено». Смена формата ответа на той стороне — это не падение сервиса, и в алерте это должно
читаться по-разному. Синтаксис самого пути валидируется при загрузке конфига, не в рантайме.

## 5. Расписание и стоимость

| Что | Частота | Стоимость |
|---|---|---|
| 5.1 HTTP liveness | 60s | 1 запрос |
| 5.2 DNS/MX | 5m | 1 UDP-запрос + ретраи |
| 5.3 Срок TLS-сертификата | из рукопожатия каждого https-чека | **0 дополнительных запросов** |
| 5.4 Срок регистрации домена | 1 раз в сутки (+ джиттер), кэш в состоянии | 1 RDAP или whois-запрос |
| 5.5 Дрейф DNS-зоны (NS/MX/A snapshot) | 1 раз в час | входит в 5.2 |

**5.4 — как получать срок домена (проверено на живых доменах 2026-08-19):**
- `.com`, `.dev` и большинство gTLD — **RDAP напрямую в реестр**. Адрес реестра берётся из
  официального бутстрапа IANA `https://data.iana.org/rdap/dns.json` (кэшировать, обновлять
  раз в неделю): `.com` → `https://rdap.verisign.com/com/v1/`, `.dev` →
  `https://pubapi.registry.google/rdap/`. Ответ — JSON, нужное поле
  `events[] where eventAction == "expiration"`. ~0.2 c. Публичные агрегаторы вроде `rdap.org`
  **не используем** — лишний посредник в цепочке доверия.
- `.ru` — **RDAP отсутствует**: в бутстрапе IANA (публикация 2026-07-23) записи `ru` нет вообще,
  как и `рф`. Проверено 2026-08-19. Только whois по **TCP/43** к
  `whois.tcinet.ru`, парсинг текстового поля `paid-till:` (плюс полезны `free-date:`, `state:`,
  `registrar:`). Реализовать сырым `net.Dial` — внешний whois-клиент в системе не нужен.
- Логика: RDAP → при 404/ошибке фолбэк на whois по таблице TLD→whois-сервер. Результат кэшировать
  в durable state (§9.1); при недоступности источника **не считать это падением домена** (отдельный статус `unknown`,
  алерт только если не удаётся обновить >3 суток).

**Вне v1: внешняя точка обзора.** Гонять часть проверок через SOCKS5, чтобы видеть публичные сайты
не из домашней сети, — полезно, но не в первой версии. Транспорт для этого всё равно появится
(алертер ходит через тот же прокси), так что добавить будет дёшево.

## 6. Пороги и уведомления

**Падение/восстановление:** `failure_threshold: 3`, `success_threshold: 2`, уведомление о
восстановлении включено. Настраивается глобально и на чек.

**Плюс детектор нестабильности — «N из последних M»** (дефолт: 5 неудач из 20). Одного «N подряд»
недостаточно принципиально: любой успех обнуляет счётчик, поэтому чередование вверх-вниз через раз
(50% доступности!) не даёт алерта никогда. Это типичная подпись одного битого бэкенда за
балансировщиком. Такое состояние сообщается отдельным текстом («нестабилен: 5 падений за 20
проверок»), а не как обычное падение, и имеет свой кулдаун.

**Уведомления по срокам (§5.3, §5.4)** — тиры, каждый порог срабатывает **ровно один раз**
(факт отправки хранится в durable state, сбрасывается при продлении):
- сертификат: 21 / 14 / 7 / 3 дня, дальше ежедневно;
- домен: 60 / 30 / 14 / 7 дней, дальше ежедневно.

**Напоминания о незакрытом падении** (`alerting.reminders`, дефолт 1h / 4h / дальше раз в сутки):
первый интервал считается от алерта DOWN, каждый следующий — от предыдущего напоминания, последнее
значение повторяется. Событие отдельного вида (`still_down`), не считается новым инцидентом и не
шлётся, если последняя проверка уже прошла успешно. Пустой список — только смены состояния.

**Содержимое алерта** (то, чего не хватало в Gatus): какое именно условие не прошло и с каким
фактическим значением, время ответа, первые 200 байт тела (HTML-оболочка отбрасывается),
длительность падения при восстановлении. Формат — короткий текст, без Markdown-разметки, которая
ломается на телах ответов.

**Форма сообщения** — читаемость важнее полноты, алерт читают с телефона:
- **одна эмодзи на сообщение**, в самом начале, по худшему событию в пачке (🔴 лежит / 🟠
  деградация или изменившийся ответ / 🟡 истекает срок / ✅ поднялось / 🔕 служебное);
- **одно событие** = заголовок-предложение («Immich is down») + максимум две строки фактов;
- **пачка** = строка-счётчик («3 down, 1 back up»), пустая строка, дальше **по одной строке на
  событие**, худшие сверху;
- **группа чека в текст не попадает**: имена чеков уникальны, а «DOWN Photos (Services)» под
  заголовком «Services 1» повторял одно и то же трижды;
- сроки — «сколько осталось + дата» («11 days left (30 Aug)»), без времени суток, без кодов
  состояния реестра и без даты освобождения домена: это жаргон, который ничьё решение не менял.
  Исключение — `undelegated`, там состояние реестра и есть содержание алерта.

**Доставка обязана переживать отказ канала — durable outbox.** Отправка алерта — это HTTP-вызов к
сервису, который сам может быть недоступен (а в нашей сети — регулярно, он ходит через прокси).
Поэтому алерт сначала записывается в очередь в durable state (§9.1), и только потом отправляется;
из очереди он удаляется лишь после подтверждённой доставки. Ретраи с экспоненциальным бэкоффом,
очередь переживает рестарт, при переполнении — схлопывание в сводку, а не молчаливая потеря.
Без этого §1.1 не выполняется: «молчание = всё хорошо» держится только если молчание не может
быть следствием сбоя доставки.

**Транспорт:** Telegram Bot API. в некоторых сетях `api.telegram.org` недоступен напрямую → HTTP-клиент
алертера обязан поддерживать SOCKS5-прокси (`socks5://gateway:1080` (адрес из конфига)). Токен и chat_id — из окружения.
Интерфейс `Notifier` — одна функция; вторая реализация (webhook) допустима, больше не надо.

**Антиспам — граф зависимостей (§7)** и окна тишины (§8).

## 7. Подавление лавины — окно батчинга

Падение шлюза или интернета не должно давать двадцать сообщений. Решение v1 — **окно батчинга**:
после первого готового к отправке алерта ждём `batch_window` (дефолт 45s), собираем все алерты,
созревшие за это окно, и шлём **одним** сообщением («🔴 12 проверок: Core — 4, Services — 5, …»,
подробности списком). Восстановления батчатся так же.

Почему так, а не граф зависимостей `depends_on`: граф выглядит умнее, но у него есть гонка —
родитель и дети достигают порога в одном и том же раунде опроса, и подавление срабатывает через
раз, в зависимости от порядка. Окно батчинга решает исходную задачу («одно сообщение вместо
двадцати») без графа, без конфигурации и без циклов в валидаторе. Если после эксплуатации
выяснится, что нужна именно причинность («упал шлюз» вместо перечисления), `depends_on` добавим
поверх батчинга — там он уже безопасен, потому что все события окна видны одновременно.

## 8. Окна тишины

`lookout mute --for 30m --group Public` (через unix-сокет или локальный HTTP-эндпоинт) и
статические окна в конфиге (cron-выражение + длительность). В окне проверки идут, алерты молчат,
на странице статуса это видно явно.

## 9. Состояние вместо базы данных

БД нет сознательно. Состояние разделено на три уровня по требованиям к долговечности:

1. **Durable state — один JSON-файл**, атомарная запись (temp + `rename`), несколько килобайт:
   текущее up/down по каждому чеку, счётчики подряд идущих успехов/неудач, время начала
   текущего инцидента, отметки об уже отправленных тирах уведомлений (§6), кэш сроков доменов
   с временем последнего успешного обновления. Пишется при каждом изменении состояния, не чаще.
   **Потеря файла не должна мешать старту**: пустое состояние = «ещё не знаю», не «всё упало»,
   и не порождает волну алертов.
2. **Недавняя история — кольцевой буфер в памяти**, последние 24 часа на чек (1440 точек:
   timestamp, ok, время ответа, код). Нужна для спарклайна, аптайма за сутки и базовой линии
   времени ответа. Рестарт её теряет — это приемлемо и не требует диска.
3. **Долгая история — append-only файл**, одна строка на чек в сутки (дата, аптайм %, число
   инцидентов, p50/p95 времени ответа), дописывается в полночь. Год работы ≈ 8 тысяч строк.
   Формат — JSON Lines, чтобы читалось чем угодно.

Инвариант: **никакая потеря состояния не должна приводить к ложным алертам** — ни к «упало»,
ни к «восстановилось». Это отдельный обязательный тест.

## 10. Интерфейсы наружу

- `GET /api/status` — JSON: все чеки, состояние, uptime 24h/7d/30d, дни до истечения серта и домена.
  Это же потребляет стартовая страница (отдельный проект) — держать стабильным, версионировать.
- `GET /api/checks/<name>` — история точками.
- `GET /metrics` — Prometheus text format (up, response_time, cert_days_left, domain_days_left).
- `GET /` — одна страница статуса: голый HTML, ноль внешних ресурсов, **ноль JS**. Группа —
  заголовок с отступом, а не колонка в каждой строке; строка раскрывается (`<details>`) и
  показывает, за чем следим, когда и почему упало в последний раз, аптайм 24h/7d/30d, медиану/p95/
  худший ответ за сутки, сроки серта и регистрации и полосу за 24 часа (48 получасовых слотов).
  Обновление — `<meta refresh>` раз в минуту: без JS раскрытая строка при этом закрывается, но
  доска, молча показывающая пятиминутной давности состояние, хуже.
- `GET /healthz` — жив сам lookout.

## 11. Безопасность

- Слушает только LAN; наружу не публикуется.
- systemd-hardening: `DynamicUser` или отдельный юзер, `NoNewPrivileges`, `ProtectSystem=strict`,
  `ProtectHome`, `PrivateTmp`, `RestrictAddressFamilies`, `CapabilityBoundingSet=`.
- Секреты только из EnvironmentFile 0600. В репозитории — `config.example.yaml` с плейсхолдерами;
  боевой конфиг (домены, IP, имена хостов) в git **не попадает**, он в .gitignore.
- Тела ответов в логи и алерты — обрезанные, с вырезанием заголовков авторизации.

## 12. Deadman

lookout следит за всеми, за самим lookout следит внешний сторож (systemd-юнит и диск хоста) —
он вне этого проекта. Дополнительно: раз в неделю heartbeat-сообщение «жив, N проверок, M инцидентов».

## 13. Тесты

- Юнит: парсер и валидатор конфига, вычисление условий, машина состояний флапа и детектор
  «N из M», тиры уведомлений, сохранение/восстановление durable state, поведение outbox при
  недоступном канале
  (таблично: не должно быть повторов), парсер whois `.ru` и RDAP (на зафиксированных фикстурах).
- Интеграционные: `httptest`-сервер на все сценарии (200/500/таймаут/битый JSON/медленный ответ),
  фейковый DNS, фейковый notifier.
- **Обязательные тесты на главные уроки:** чек без явного `alert:` обязан алертить; сбой доставки
  не теряет алерт (outbox переживает рестарт); потеря файла состояния не порождает ни одного
  ложного алерта.
- Время в тестах — через `testing/synctest` (в stdlib с Go 1.25, фейковые часы): интервалы,
  бэкоффы и окна батчинга тестируются без `time.Sleep` и без флейков.
- CI (Forgejo Actions): `go vet`, `go test -race`, `staticcheck`, `govulncheck`, сборка.

## 14. Что переносим из Gatus

Инвентарь переносимых проверок ведётся вне этого репозитория (приватный инфра-репо).
Приёмка: lookout работает **параллельно** со старым монитором на другом порту; сверяем неделю; расхождение в
любую сторону разбираем до переключения.

## 15. Порядок работ

0. Ресёрч best practices (отдельный отчёт до кода).
1. Конфиг + валидатор + модель чеков. 2. HTTP-чек + условия. 3. Машина состояний (пороги +
детектор «N из M») + durable state. 4. Алертер: outbox + батчинг + Telegram через SOCKS5.
5. API/страница/метрики. 6. DNS + дрейф зоны. 7. Сроки сертификатов и доменов + тиры.
8. Окна тишины. 9. systemd + деплой + параллельный прогон со старым монитором.
